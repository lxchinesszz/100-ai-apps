# 技术方案：新 App 识别与归档流程

## 现状分析

`AGENTS.md` 的 3.3 节只区分具体 App 与仓库公共能力，4 至 7 节定义需求目录、总清单和模板，但缺少新 App 从“尚无目录”到“建立首份 App 级需求”的启动规则。现有 `apps/` 已包含带三位数字前缀的目录，适合明确统一的递增命名方式。

## 方案设计

在 `AGENTS.md` 的 Mandatory Change Workflow 中增加独立的新需求归属与新 App 启动规则，并同步调整标准流程说明：

1. 将入口判断细化为明确指定 App、匹配已有 App、新 App、仓库公共能力四种情况。
2. 明确用户已指定时不重复确认；未指定时扫描 `apps/`，只推荐最匹配的一项。
3. 新 App 通过单轮单问澄清核心用途，再提出规范目录名并等待确认。
4. 目录序号使用现有合法数字前缀最大值加一，名称使用英文 kebab-case。
5. 增加启动例外：目录名确认后，可一次创建 App 目录、App 级需求总清单和首个需求目录。
6. 首个需求目录复制全局模板的三份文档并登记 `Proposed`，后续访谈持续更新。
7. 明确初始化阶段禁止生成应用代码，代码仍受方案确认 Gate 约束。
8. 在 App 级需求章节补充后续归档的持续性约束，避免需求回流根级目录。

## 兼容性与风险

- 兼容性：仅调整仓库协作规则，不影响现有 App 运行。
- 风险：目录扫描可能遇到无数字前缀或命名异常目录；序号计算只采用合法的三位数字前缀，异常目录不参与递增。
- 风险：用户目标过于模糊时无法可靠命名；继续按单轮单问澄清，未确认名称前不得创建目录。
- 风险：首次建档例外可能被误用为提前编码；规则明确允许的写入范围仅为目录与需求文档结构。

## 验证方案

1. 静态检查 `AGENTS.md` 是否逐项覆盖需求中的十一条业务规则。
2. 使用已有 App、明确指定 App、无匹配新 App和仓库公共需求四类场景进行规则走查。
3. 检查首次建档例外与方案确认 Gate 是否不存在冲突。
4. 检查 Git 改动范围，确保未修改任何现有 App。
5. 由只读 Tester 独立对照九条验收标准给出 PASS / FAIL。
