# 通用开发规范

本规范适用于 `100-ai-apps` 仓库中的所有 App。

它只定义跨平台公共开发规则，不负责需求流转，也不替代具体平台规则。

规则加载顺序遵循根目录 `AGENTS.md`：

```text
AGENTS.md
↓
rules/common/README.md
↓
rules/<platform>/README.md
↓
当前 App 的需求与技术方案
```

如果本规范与具体平台规则存在冲突，以更具体的平台规则和当前已确认需求为准。

---

## 1. 产品原则

### 1.1 一个 App 优先解决一个明确问题

每个 App 必须有清晰的核心问题和核心用户价值。

不要因为“以后可能需要”而提前加入大量功能。

优先问：

```text
用户现在最需要完成什么？
↓
最短路径是什么？
↓
什么是完成这个目标的最小闭环？
```

### 1.2 MVP First

第一版优先完成可运行、可验证、可使用的最小产品。

禁止为了“完整”而一次性加入：

```text
复杂账号体系
复杂权限体系
多角色后台
多租户
消息中心
运营平台
数据大屏
推荐系统
插件体系
微服务
```

除非当前需求明确需要。

### 1.3 核心流程优先

开发顺序优先保证：

```text
主任务入口
↓
核心操作
↓
结果反馈
↓
数据保存
↓
再次进入后仍可继续使用
```

辅助能力、装饰性功能和低频设置后置。

### 1.4 需求之外不主动扩展

Agent 不得因为发现“可以顺便做”就扩大需求范围。

发现额外问题时：

- 可以记录。
- 可以提出建议。
- 不应未经确认直接实现。

## 2. 技术原则

### 2.1 简单优先

在满足需求的前提下，优先选择：

```text
更少的模块
更少的依赖
更少的运行时
更少的外部服务
更直接的数据流
更容易理解的实现
```

复杂方案必须由明确需求驱动。

### 2.2 不为未来过度设计

禁止仅因为“以后可能扩展”而提前引入：

```text
复杂分层
通用框架封装
大型状态管理
事件总线
插件系统
微前端
微服务
消息队列
分布式架构
```

只有当当前 App 已出现真实复杂度时再升级。

### 2.3 依赖最小化

新增依赖前必须判断：

1. 原生能力是否已经足够。
2. 现有依赖是否已经能完成。
3. 新依赖是否真的降低复杂度。
4. 是否会明显增加包体积、维护成本或平台风险。

不要为了一个很小的功能引入大型依赖。

### 2.4 优先使用稳定能力

优先成熟、稳定、文档清晰的技术。

除非需求本身是为了研究新技术，否则不要为了“新”而替换稳定方案。

### 2.5 平台能力服从平台规则

跨平台规则不直接决定：

- 路由实现。
- 本地存储 API。
- 文件系统。
- 网络 API。
- 打包方式。
- 发布方式。

这些由 `rules/<platform>/` 决定。

## 3. UI / UX 基线

### 3.1 先做信息层级，再做视觉装饰

页面首先要回答：

```text
我现在在哪？
我能做什么？
最重要的操作是什么？
操作之后发生了什么？
```

视觉设计应服务于信息层级，而不是反过来。

### 3.2 核心操作必须突出

每个页面应有明确主操作。

不要让多个同等级按钮争夺注意力。

优先形成：

```text
Primary Action
Secondary Action
辅助操作
```

### 3.3 避免无意义卡片化

不要为了“看起来像产品”把所有内容都装进卡片。

如果信息之间属于同一层级，可以直接使用：

```text
分组
留白
分隔线
标题层级
列表
```

卡片应该有明确的语义边界。

### 3.4 必须设计完整状态

重要页面不能只设计“正常有数据”的状态。

至少考虑：

```text
Loading
Empty
Success
Error
Disabled
No Permission（如适用）
Offline（如适用）
```

空状态不能只留空白，应告诉用户下一步可以做什么。

### 3.5 反馈必须及时

用户完成关键操作后，要有明确反馈。

例如：

```text
保存成功
删除成功
提交成功
同步中
失败原因
可重试
```

不要让用户猜测操作是否生效。

### 3.6 危险操作必须明确

删除、覆盖、清空、重置等不可逆或高风险操作，应提供：

- 明确文案。
- 二次确认，或可撤销机制。
- 清晰说明影响范围。

### 3.7 不依赖隐藏交互完成核心任务

核心功能不能只通过：

```text
Hover
长按
右键
隐藏手势
隐藏快捷键
```

触发。

这些能力可以作为快捷入口，但必须存在可发现的正常入口。

### 3.8 保持一致性

同一个 App 内相同语义应保持一致：

- 相同操作使用相同文案。
- 相同状态使用相同视觉表达。
- 相同层级使用相同组件和间距体系。
- 不在不同页面随意改变交互模式。

## 4. 编码规范

### 4.1 可读性优先

代码首先应该让下一个开发者或 Agent 容易理解。

避免：

```text
过度技巧化写法
为了少几行代码牺牲可读性
难以理解的链式逻辑
大量隐式副作用
```

### 4.2 单一职责

一个模块、组件或函数应尽量只承担一个清晰职责。

当一个文件同时负责：

```text
UI
业务规则
数据持久化
网络请求
格式转换
复杂状态
```

通常说明需要拆分。

但不要为了“形式上的分层”把简单逻辑拆得过碎。

### 4.3 控制文件与组件复杂度

出现以下信号时，应考虑拆分：

- 文件已经难以快速理解。
- 同一组件包含多个明显独立区域。
- 一个函数存在大量分支和副作用。
- 修改一个小功能需要理解整份大文件。
- 相同逻辑开始在多个位置复制。

不要机械按固定行数拆分，按职责拆分。

### 4.4 避免重复业务逻辑

相同业务规则出现两次以上时，应判断是否抽取。

优先抽取：

```text
业务计算
校验规则
数据转换
持久化逻辑
公共状态判断
```

但纯展示结构相似不代表一定需要抽象成通用组件。

### 4.5 避免过度抽象

不要提前创造：

```text
BaseXXX
AbstractXXX
通用万能组件
万能 Hook
万能 Service
复杂配置驱动框架
```

如果当前只有一个真实使用场景，优先写清楚当前实现。

当第二、第三个真实场景出现后，再抽取稳定共性。

### 4.6 命名表达业务含义

变量、函数、组件、文件命名要表达真实用途。

优先：

```text
calculateRemainingBudget
saveTrainingProgress
CheckInHistory
```

避免：

```text
data
info
temp
handleThing
processData2
```

### 4.7 避免魔法值

有明确业务含义的数字、字符串、状态值，应使用有语义的常量或类型。

例如：

```text
MAX_DAILY_TASKS
DEFAULT_BUDGET
STATUS_COMPLETED
```

### 4.8 错误不要静默吞掉

禁止无处理地：

```text
catch (e) {}
```

错误至少应做到其中之一：

- 给用户反馈。
- 记录可诊断信息。
- 提供降级结果。
- 明确重试方式。

### 4.9 注释解释“为什么”

不要用注释重复代码已经表达的内容。

注释优先解释：

```text
为什么这样做
为什么不能使用另一种方案
平台限制
业务边界
兼容性原因
```

## 5. 数据与状态

### 5.1 数据模型先于页面拼装

涉及持久化数据时，先明确数据模型，再写页面逻辑。

至少明确：

```text
字段
类型
默认值
唯一标识
时间字段
状态字段
版本字段（如需要）
```

### 5.2 区分业务数据与 UI 状态

不要把所有状态混在一起。

应区分：

```text
业务数据
用户设置
临时表单状态
Loading / Error
页面展示状态
缓存数据
```

持久化业务数据时，不应无意义保存纯 UI 临时状态。

### 5.3 持久化要可靠

如果需求要求保存，刷新、重启或重新进入应用后不应无故丢失。

写入失败时不能假装成功。

### 5.4 数据结构要考虑升级

一旦数据会被长期保存在用户设备或文件中，就要考虑未来字段变化。

至少应避免：

```text
读取旧数据直接崩溃
字段缺失导致整个应用不可用
新版本覆盖旧数据且无法恢复
```

复杂数据结构应有明确版本或迁移策略。

### 5.5 删除数据要明确范围

执行删除、清空、重置时，必须明确删除的是：

```text
单条记录
当前项目
当前用户数据
全部本地数据
缓存
设置
```

不能使用模糊的“清理数据”实现大范围删除。

### 5.6 不存储不需要的数据

只保存业务真正需要的数据。

不要因为“以后可能分析”就长期保存大量无用行为数据、临时数据或敏感数据。

### 5.7 敏感信息最小化

如果业务确实涉及令牌、账号、个人信息或其他敏感数据：

- 最小化收集。
- 最小化保存时间。
- 不写入源码。
- 不写入公开日志。
- 不提交真实密钥到 Git。

具体安全能力按平台规则实现。

## 6. 测试与验证

### 6.1 Build 必须通过

只要项目存在标准构建流程，完成改动后必须执行对应构建验证。

不能以“代码看起来没问题”代替 Build。

### 6.2 核心流程必须验证

至少验证当前需求涉及的核心闭环。

例如：

```text
进入页面
↓
执行核心操作
↓
结果正确
↓
数据保存
↓
重新进入
↓
状态仍然正确
```

### 6.3 不能只测 Happy Path

根据需求至少检查相关边界：

```text
空数据
非法输入
极小值 / 极大值
重复操作
快速连续点击
失败状态
刷新 / 重启
数据缺失
权限拒绝（如适用）
网络异常（如适用）
```

不是所有项目都需要全部场景，只检查与当前能力相关的边界。

### 6.4 Bug 修复必须验证原问题

修 Bug 时，不能只验证“新代码能跑”。

必须验证：

```text
原问题可以复现
↓
修改后原问题消失
↓
相关正常流程未被破坏
```

### 6.5 不伪造测试结果

没有执行的测试不能写成“通过”。

如果受环境限制无法验证，必须明确写：

```text
未验证
原因
风险
建议验证方式
```

### 6.6 验证结果必须可追踪

完成需求后，将真实验证命令和结果记录到对应 `change-list.md`。

## 7. 交付规范

### 7.1 App 必须可独立理解

每个 App 至少应有基础说明，使新的开发者或 Agent 能理解：

```text
这个 App 是什么
解决什么问题
如何启动
如何构建
如何验证
如何部署（如适用）
关键技术约束
```

具体放在 App README、APP.md 或项目既有说明文件中，由当前 App 结构决定。

### 7.2 运行方式必须明确

不要只留下源码。

应明确实际可执行命令，例如：

```text
安装依赖
开发运行
构建
测试
预览
```

仅记录项目真实支持的命令，不虚构脚本。

### 7.3 部署方式必须明确

如果 App 需要发布，必须说明：

```text
构建产物是什么
部署到哪里
需要哪些配置
访问入口是什么
部署后如何验收
```

具体部署细节遵循对应平台规则。

### 7.4 已知限制必须记录

如果存在没有解决的问题、平台限制、兼容性问题或暂不支持的能力，应明确记录。

不要为了看起来“完成”而隐藏限制。

### 7.5 不提交临时垃圾文件

不得把无意义的本地临时产物提交到仓库，例如：

```text
编辑器缓存
系统临时文件
调试 dump
本地密钥
无用构建产物
随机测试文件
```

除非仓库明确要求保留某类生成文件。

## 8. AI Coding 约束

### 8.1 开发前先理解上下文

Agent 开始修改代码前，应按当前任务读取：

```text
AGENTS.md
↓
rules/common/README.md
↓
对应平台规则
↓
当前需求文档
↓
相关现有代码
```

不要在不了解现有实现时直接重写。

### 8.2 优先修改现有实现

已有稳定结构时，优先在现有架构内完成需求。

不要因为 AI 更熟悉另一套方案就：

```text
重建项目
替换框架
替换路由
替换状态管理
替换 UI 体系
重写整个页面
```

除非技术方案已经明确要求。

### 8.3 最小改动范围

只修改完成当前需求真正需要的文件。

避免：

```text
顺手格式化整个仓库
顺手重命名大量文件
顺手升级所有依赖
顺手做无关重构
```

### 8.4 修改后必须自检

至少检查：

```text
是否符合需求
是否符合 common 规则
是否符合平台规则
是否引入无关依赖
是否破坏已有能力
是否完成构建 / 测试 / 人工验证
```

### 8.5 不用猜测代替核验

涉及已有代码、脚本、配置、路径、API、数据模型时，优先读取和核验真实内容。

不要仅根据文件名或惯例猜测。

### 8.6 发现冲突时遵循优先级

如果当前实现与规则冲突，不应静默选择其中一个。

按照 `AGENTS.md` 的优先级执行：

```text
用户当前明确指令
↓
当前需求 / 已确认技术方案
↓
具体平台规则
↓
通用规则
↓
AGENTS.md
↓
既有实现习惯
```

### 8.7 完成意味着可验证

AI 的完成标准不是“代码已经生成”，而是：

```text
需求已经实现
+
构建或运行验证通过
+
核心流程验证通过
+
异常与边界已检查
+
文档已同步
+
结果可被用户验收
```

## 9. 通用完成检查清单

每次 App 需求实施完成后，至少检查与当前需求相关的项目：

- [ ] 核心用户目标可以完成。
- [ ] 没有实现需求范围外的无关功能。
- [ ] 没有无必要增加架构复杂度。
- [ ] 没有无必要增加大型依赖。
- [ ] 页面主操作清晰。
- [ ] Loading / Empty / Error 等必要状态已处理。
- [ ] 危险操作有合理保护。
- [ ] 数据模型和持久化行为符合需求。
- [ ] 重新进入应用后需要保留的数据仍然存在。
- [ ] 错误没有被静默吞掉。
- [ ] Build / 编译可以通过。
- [ ] 当前需求核心流程已验证。
- [ ] 相关异常和边界场景已检查。
- [ ] 没有提交密钥或临时垃圾文件。
- [ ] 运行、构建、部署或已知限制已按需记录。
- [ ] 对应需求文档和 change-list 已同步真实结果。

---

## 10. 最终原则

> 一个 App 先把一个问题解决好，再考虑扩展。

> 能用简单方案解决的问题，不主动升级成复杂系统。

> UI 不只要“能看”，还要让用户知道下一步做什么。

> 数据只要承诺保存，就必须可靠保存。

> 代码首先服务于可理解、可维护和可验证，而不是炫技。

> AI 不以生成代码为完成标准，以真实产品结果通过验收为完成标准。
